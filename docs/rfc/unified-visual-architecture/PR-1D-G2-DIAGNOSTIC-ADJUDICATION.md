## GC 契約裁決

[Storage Lifecycle 的 GC 與 FG-01/02](STORAGE-LIFECYCLE.md)、[實作報告 §6](https://github.com/Curium-3391/Estampes/blob/d9aaa49f27d195ed53baeb12e95e434f1a7b10b0/docs/rfc/unified-visual-architecture/PR-1D-IMPLEMENTATION-REPORT.md)、[State Machine Hardening](PR-1D-STATE-MACHINE-HARDENING-REPORT.md) 與 [Test Matrix 的 UVA-47/49、64](https://github.com/Curium-3391/Estampes/blob/d9aaa49f27d195ed53baeb12e95e434f1a7b10b0/docs/rfc/unified-visual-architecture/TEST-MATRIX.md) 要求已選且可驗證的計畫、24 小時 G2 grace、重新 mark、unlink intent 和實體刪除的 fsync。文件描述有界 candidate work 和分批發布，未為所有合法計畫定義 grace 後一次呼叫必達 terminal 的 SLA，也未明列 grace 後所有回傳狀態與各種阻擋理由的對應。名稱 `waiting-grace` 本身也不足以判定剩餘工作只在等時鐘。

基準的 `GarbageCollector.step` 嘗試隔離每個未 moved 的候選，發布 quarantine progress，重新 mark 後逐一檢查 moved 候選。若可 unlink，先發布選取的 `unlinking` indexes，再做最後一次 mark、驗證 inode／hash／length、unlink 和 directory fsync，最後發布 progress。只有所選 `deleted` 涵蓋計畫內每個 index 才為 `complete`。已刪除的 index 釋放該物件的 ownership。單一計畫最多 128 個候選，跨 active 計畫最多 4096 個，temporary dispositions 每 plan 最多 64 個。此實作沒有額外的 `gcStep` operation counter 或時間切片，也沒有「每次最多 N 個 unlink」的停止點。每個 Root transaction 的 staging 限制獨立計算。容量或 barrier 失敗走錯誤／recovery 路徑，不能以已成功回傳的狀態字串證明尚有 fsync 在背景等待。[GC plan 與 step](../../../src/persistence/gc.js#L96) · [GC ownership](../../../src/persistence/gc.js#L52) · [Filesystem barriers](../../../src/persistence/filesystem.js#L158) · [Maintenance dispatch](../../../src/persistence/lifecycle.js#L89)

`quarantining` 有兩種需要分辨的觀測點。一次 `gcStep` 內，`gc-quarantine-progress` 會先持久化這個中間態，即使最後能在同一次呼叫完成。作為 `gcStep` 回傳時，分支條件是仍有未刪 index 且該步沒有為 moved 候選設下 `waiting`。例如某 index 在第一輪 mark 時受保護而從未 moved，其餘候選均已刪除，就可能合法回傳 `quarantining`。已 moved 的物件因重 mark 或 grace 不能 unlink 時會設下 `waiting`。候選仍受保護時可維持未完成，解除保護後需要再呼叫同一計畫。此 fixture 的 auto-maintenance 關閉。已過 grace、無保護且所有候選可處理時，現行迴圈會在同一步嘗試完成，仍須以選取的 progress 和檔案狀態核對是否達成。

原斷言可當作這個固定 fixture 的進度回歸檢查，但只由時鐘推出 `complete` 超出一般維護契約。若後續證明原失敗由合法保護造成，最小 oracle 修正是保留 grace 前零刪除、唯一 Ledger／精確 ACK、候選 ownership 與 closure 斷言。第一步未完成時要求每個 pending index 都有具名的合法阻擋或已證明的 in-flight recovery，並在條件解除後以有界呼叫驗證同一計畫 terminal。若候選已可刪除且無阻擋，保留同一步完成的嚴格斷言。原 test 保留。

## 狀態轉換與裁決

四次嚴格重現及 bounded-drain 控制在初次 kill 後仍是 generation 1，四次 recovery SIGKILL 後依序選取 generations 2–5，Ledger 均為 0。成功 recovery 到 generation 6，提交到 7 並建立唯一 Ledger entry，重開到 8 取得原 ACK。GC 的選取序列為 generation 9 `planned` → 10 `quarantining`（12 moved）→ 11 `waiting-grace`（0 deleted）→ 12 clock observation → 13 `quarantining` → 14 `unlinking`（indexes 0–11）→ 15 `complete`（12 deleted、0 pending）。冷重開到 16，維持 terminal、單一 Ledger 與唯一完整 Locator representation。無中斷 recovery 控制於 generation 11 刪完 8 個候選，generation 12 冷開後同樣穩定。

所有有診斷案例的 `quarantining` 都是有 fsync 證據的步內發布。第一次的 pending 是已隔離、仍由所選 plan 持有的候選，受 G2 grace 限制。第二次的 pending 仍由同一 plan 持有，clock／high-water 均為 `1893542400000`，恰好等於 `1893456000000 + 86400000` 的期限，aging 啟用。隔離檔的 dev/inode、bytes 與 hash 均匹配。GC 採樣的 production mark 無候選來源命中，runtime reader pins 與 backup jobs 為空。第二步在原呼叫內發布 unlink intent、完成所有 unlink 與目錄 fsync、發布 terminal，沒有耗盡的 step budget 或待完成的 barrier。六例都無需追加 maintenance 呼叫。採樣上限為 192 files、929,792 allocated bytes。

原始 #131 回傳的 `quarantining` 是唯一一筆未釐清的外部回傳。缺少它當次選取的 plan ID／hash／generation、候選 path 和 inode、moved／unlinking／deleted／pending indexes、source 和 quarantine 位置與 hash／length，以及當時的 live／recovery Root、pin、backup re-mark。也缺實際 grace anchor／high-water、GC 回傳的 progress counters、每次 fsync／publication 的邊界與同一 Store 的後續 step／冷重開結果。因此當次剩餘候選、選取 ownership、個別阻擋、grace eligibility、持久化狀態與可恢復性無法從原始證據逐項回答。固定預算重跑能顯示受測序列可完成，不能回填原失敗。分類維持 **C — UNRESOLVED INTERMITTENT**。

最小後續是下一次執行原始 native suite 時保留第一筆非預期回傳的選取 plan、候選 re-mark 和 barrier trace，讓同一 disposable Store 存活到有界的同計畫重試及冷重開。依該筆證據再決定是合法延後或需要最小 state transition 修復。
