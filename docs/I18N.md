# Interface languages

Estampes ships English (`en`) and Traditional Chinese (`zh-TW`). This page explains how the language is chosen, which text is translated and which is not, and how to add a language. The design and its decisions are in the [multilingual RFC](rfc/i18n/README.md).

## How the language is chosen

Each view (canvas, Store, calculator) picks its language on its own, first match wins:

1. the language the person picked in the view's **Language** menu (kept in that browser only, never in a shared canvas);
2. the chat app's language, when the host reports one (MCP Apps `hostContext.locale`, or `openai.locale`); set `ESTAMPES_LOCALE_FROM_HOST=0` to ignore it;
3. `ESTAMPES_DEFAULT_LOCALE` for the instance;
4. English.

A tag is matched to a shipped language by exact tag, then by script or region (`zh-Hant`, `zh-HK` → `zh-TW`; `zh-Hans` and `zh-CN` never become `zh-TW`), then by bare language (`en-GB` → `en`). The OAuth sign-in page follows the browser's `Accept-Language`.

## What is translated, and what is not

| Text | Language |
| --- | --- |
| Widget text: buttons, menus, status lines, error sentences for known server codes | The view's language |
| A message the canvas posts as the person (marks sent, verdicts, hand edits, number line) | One sentence in the person's language, then an English block for the assistant that is the same in every language |
| Tool descriptions, tool results and other text the assistant reads | English only, so the assistant behaves the same whatever the person's language |
| Default names the server stores (「AI · 第2次」, "Workspace (split)") | Stored as the literal text plus a catalog key (`nameKey`, `nameParams`), so the canvas shows them in the viewer's language; the assistant reads the literal. A record without a key, or renamed by the person, shows its literal text |
| Text the person or the assistant typed (labels, notes, names) | Never translated |
| Runtime text from modules (result summaries, info cards) | As the module wrote it. Module translations are planned for module system v2 (RFC §6.3) |

## Adding a language

1. **Catalog.** Copy `src/i18n/locales/zh-TW.json` (the reference catalog) to `src/i18n/locales/<tag>.json` and translate every value. Set `i18n.autonym` to the language's name in itself; the Language menu shows it. The server picks up every `*.json` in that folder; no list to edit.
2. **Parameters and plurals.** Keep every `{param}` of the reference message, with the same names. Plurals use ICU syntax (`{count, plural, one {# item} other {# items}}`) and the language's own categories from `Intl.PluralRules`. A message must not contain a literal `{` or `}`: pass such text as a parameter.
3. **Default names (`name.*`).** Keys under `name.` are listed in `NAME_KEYS` (`src/i18n/names.js`) and need a message in every catalog, with the same parameters as `zh-TW`. Stored records keep their key, so a new language needs no migration: old and new default names show in it as soon as the catalog exists. `name.author.user` and `name.author.assistant` turn the author token into a word. To add a new default name, add the key to `NAME_KEYS` and both catalogs, and create it with `defaultName(key, params)`. Never build a default name from `t()` alone, or it will not follow the viewer's language.
4. **HTML language tag.** If the catalog tag is not the tag pages should declare (as `zh-TW` declares `zh-Hant`), add it to `LANG_TAGS` in `src/i18n/index.js`.
5. **Tag matching.** `matchLocale` in `src/i18n/widget-runtime.js` maps a bare language to your catalog (`fr-CA` → `fr`). Chinese has its own rule; add one only if your language has scripts or regions that must not share a catalog.
6. **Fonts.** Server-side drawing (`render_canvas`) uses fonts in the image: DejaVu and Noto Sans CJK. For other scripts, mount a fonts folder ([Deployment](DEPLOYMENT.md)).
7. **Right-to-left languages** are not supported yet: pages are rendered with `dir="ltr"`. RTL support will be added when the first RTL language is requested (RFC §7).
8. **Check.** Run `npm run i18n:check -- --strict` (it fails on a missing key, a message that does not parse, or parameters that differ from `zh-TW`) and `npm test`. Then open the canvas, pick the language in the Language menu, and look at the layer list, the text editor, the Store and the calculator.

Do not translate the English assistant blocks in `src/interaction-protocol.js` and `src/surface/user-voice.js`, tool descriptions, or any other text the assistant reads.

## Writing new text

Put every new string the person sees in both catalogs and read it with `t("key", params)` (server) or `i18nT` (widgets). `npm run i18n:check -- --strict`, run in CI, fails on hard-coded CJK text in code. A table built once at start-up should use `i18nMap({ k: "key" })`, so it follows a language change. Model-facing text stays English.
