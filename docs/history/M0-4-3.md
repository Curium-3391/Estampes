# Estampes M0.4.3 — Visual Input Bridge (experimental)

## Purpose

In M0.4.2 ChatGPT received the geometry of a user's mark but often **could not identify the marked object**. A coordinate is not a picture. M0.4.3 introduces the first *model-callable pixel evidence* tool:

`inspect_visual(scene, imageId, revision, focus[, padding])`

**Boundary:** Estampes knows pixel bytes, scale, crop and annotation geometry. GPT is responsible for semantic identification. The tool does **not** say that a point is a house, a tree, or a mountain, and must not transform human-supplied labels into proven visual facts.

## Tool input

```json
{
  "scene": "landscape",
  "imageId": "demo:landscape",
  "revision": "svg-v1",
  "focus": {
    "type": "rect",
    "x": 0.1,
    "y": 0.42,
    "x2": 0.4,
    "y2": 0.92
  },
  "padding": 0.08
}
```

For `point`, only x/y. For `arrow`, x/y is the tail, x2/y2 is the **target**; the crop focuses on the arrowhead.

The tool only accepts `demo:landscape`, `demo:shapes` and `demo:formula` at revision `svg-v1`. The original art is parsed from the exact same trusted `public/visual-surface.html` used by the widget; no network downloads, arbitrary URLs or user-supplied SVG execution.

## Tool output

The MCP `content` array contains:

1. Text describing the image *identity, crop geometry and source dimensions*, **without guessing the depicted objects**.
2. `type:"image", mimeType:"image/png"`: original full picture, no overlays.
3. `type:"image", mimeType:"image/png"`: the full picture with a blue location overlay.
4. `type:"image", mimeType:"image/png"`: 2× enlarged **unmarked** crop near the selected point or region.

`structuredContent` includes:
- `kind:"estampes.visual_evidence"`, `imageId`, `revision`
- original vector logical size 640×360 **SVG user units**
- rasterized full PNG size 640×360 **pixels**
- normalized focus and crop rectangle in **rendered source pixel** coordinates
- `evidenceCount:3`
- `modelVisionStatus:"host-dependent-unverified"`

The full unmarked original is essential: edge maps, overlays and crops may hide scene context or details. The crop is auxiliary evidence, not a replacement for the original image.

## ChatGPT host limitation

The MCP spec formally supports base64 image blocks inside tool results: [MCP 2026-07-28 Tools specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx).

However **a valid MCP tool image block does not guarantee ChatGPT passes that block to the model's vision input**. An [OpenAI Developer Community answer](https://community.openai.com/t/chatgpt-connector-returns-empty-for-mcp-tool-results-with-type-image-while-same-tool-works-in-mcp-inspector/1375446/5) discusses this integration limitation. Therefore:
- **MCP wire correctness** can be checked with an MCP client/integration tests.
- **Model perception** must be separately established through a real ChatGPT test.
- A GPT reply that simply names an object based on `scene=landscape` is **not proof** it has seen any pixels.
- If image content is hidden, GPT must say it cannot inspect the picture instead of guessing.

For true vision support on such hosts, a later iteration may use a host-supported file/image attachment API or an explicit vision-capable model call with user-approved image data. Neither is implemented by this milestone.

## Acceptance procedure

1. Wait for Render to show the latest commit Live, open [version endpoint](https://estampes-mcp.onrender.com/version); verify `m0.4.3` and `visualInputTool:inspect_visual`.
2. Refresh the Estampes custom plugin tool definitions in ChatGPT.
3. In a new chat, open the `landscape` visual surface and mark **the house with a rectangle** plus **the tree crown with a point**.
4. Give a free-text note such as **「請辨識這兩個標註所指的東西」** and send.
5. Check that GPT calls **`inspect_visual` once for each relevant mark**, supplying the correct `imageId`, `revision` and the original `focus` coordinates.
6. Inspect the output of each `inspect_visual` tool call. The MCP response must contain 3 PNG image content blocks. **This alone does not certify model vision.**
7. To test vision rather than coordinate guessing, ask GPT to describe a genuinely visible detail not embedded in scene metadata/tool descriptions (e.g. approximate color or arrangement in the returned PNG); do not count a guessed object name as success. Record whether image blocks were visibly accessible to the model.
8. If the model cannot access pixels, log this as a **host vision-bridge failure**, not an Estampes geometric failure.

## Automated tests

Run `npm install --no-audit --no-fund && npm test`. The Render Blueprint executes the same build sequence. Tests now check:
- source SVG scene extraction matches the widget code
- actual PNG headers and non-placeholder pixel content
- overlay image differs from the pristine source
- exact crop geometry at edges, reversed boxes, and arrowheads
- rejection of invalid image IDs, revisions, and out-of-range coordinates
- full MCP tool discovery, result geometry, and three base64 PNG image blocks.

## Not implemented

- Importing arbitrary local pictures, ChatGPT image search results, or screenshots from another app
- General semantic grounding, OCR, detection, segmentation, edge snapping
- Guarantee that the ChatGPT host displays tool-returned pixels to GPT vision
- Persistent shared annotation state or authenticated image provenance

**Privacy:** Demo scenes only. The public Render MCP endpoint has no authentication; do not send personal images or confidential text to this proof of concept.
