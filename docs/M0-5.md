# Estampes M0.5 — Real-image preprocessing tools

## Goal

Let GPT work with real pictures (PCB photos, blurry scans, handwriting, book
pages, physical models) by giving it pixel tools, without adding an Estampes
upload UI. Estampes transforms pixels and keeps coordinates honest; GPT still
does all recognition.

## Image intake (ChatGPT-native only)

- **Attached or photographed in the chat:** `load_image.image` is declared in
  `_meta["openai/fileParams"]`, so ChatGPT passes the conversation file as
  `{download_url, file_id, mime_type?, file_name?}`. The server downloads it.
- **Found by GPT:** `load_image.imageUrl` takes a public https URL. Only public
  addresses are fetched (no localhost/LAN/metadata IPs, redirects re-checked),
  max 20 MB, 15 s, 50 megapixels.
- **Generated by GPT:** not yet known whether ChatGPT can pass generated images
  as file params; to be checked live.

Images are decoded with sharp, EXIF-rotated, capped at 4096 px on the long side
and kept in memory only (about an hour, at most 12 images / 160 MB). The
download URL is never logged or echoed.

## Tools

| Tool | Purpose |
| --- | --- |
| `load_image` | Register an image, return `imageId` and a preview for the model. |
| `process_image` | Optional `region` crop (zoomed up to 8×) then `ops` in order: `grayscale`, `normalize`, `clahe`, `contrast`, `brightness`, `sharpen`, `denoise`, `threshold` (adaptive / otsu / fixed), `invert`, `edges`. |
| `overlay_grid` | Labelled grid (rows A…, columns 1…) over the image or a region; `cellCenters` gives each cell's centre in source coordinates for `present_visual`. Call again on a cell to refine. |

Suggested recipes: blurry scans and glare → `clahe, sharpen`; handwriting and
book pages → `grayscale, threshold(adaptive)`; PCB traces and line art →
`edges` (or `clahe` then `edges`).

## Coordinate invariant

Every output reports the `region` it covers, normalized to the full oriented
source image (top-left origin). A point (u, v) in an output maps to
`x = region.x + u·(region.x2 − region.x)`, likewise for y. Operations never
rotate or warp, so this mapping is exact.

## Display

Image tool outputs are image blocks for the model. What the user sees is the
`present_visual` canvas (M0.5.1):

- `present_visual({imageId, annotations, views?})` shows the real photo.
  It opens on the **original** (with GPT's gold marks on the 標註與編輯 tab and
  a clean 原始圖片 tab), matching the "default to the original" requirement.
- `views` (max 3, each `{label, ops, region?}`) are optional extra tabs with
  processed pixels (e.g. clahe+sharpen, threshold, a zoomed region). They
  are drawn at their source region, so coordinates stay consistent.
- Pixels travel in widget-only `_meta` (`estampes/image`, `estampes/views`);
  the model gets geometry only. Display JPEG long side ≤ 1600; large views are
  re-encoded to JPEG.
- The user can draw blue marks on the photo and send them back.
  `validate_visual_annotations({imageId,...})` builds a raster event, and the
  chat message tells GPT to inspect the marked spot with `process_image`.
- No upload UI: the photo still enters only through ChatGPT's own file
  handling (`load_image`).
- Polylines (0.5.3): a fourth mark type for paths such as PCB traces and
  wires, and the user's freehand drawing. GPT passes `{type:"polyline", points:[{x,y},…]}` (2–128 ordered
  vertices); the server adds the bounding box as x/y/x2/y2 so zoom and
  `process_image` regions work unchanged. The user draws with the 手繪
  tool: mouse, drawing tablet, Apple Pencil or S Pen through Pointer Events,
  including coalesced pen samples. Strokes are simplified with
  Ramer–Douglas–Peucker (keeps corners) to at most 128 points; each stroke is
  one mark (max 30 per send).
  A polyline is only GPT's reading of visible copper; hidden parts (under
  components, inner layers, the back side) must be said, not guessed.

## Trial feedback round (0.5.3)

GPT's own review after a live trial: the core loop works (user boxes one
chip, GPT inspects that region and reads CXD2500AQ, no re-screenshot), but
four frictions. What changed:

- **Latency.** Cached pixels are raw (no PNG decode per call), colour
  outputs encode straight to JPEG, the display image is cached per photo,
  and CLAHE is a JS implementation (libvips' local histogram took ~1.8 s on
  a 1600 px crop; now ~0.2 s). `present_visual` also accepts the attached
  file (`image`) or `imageUrl` directly, so "show me / circle this" is one
  call instead of load_image + present_visual.
- **Focus vs background marks.** Each submission marks the newly drawn
  marks `role:"focus"` and marks already sent `role:"context"`; sent marks
  fade, and the chat message names the focus mark and tells GPT to treat
  the rest as background.
- **No tool names for users.** Tool descriptions tell GPT that users will
  not name tools and that it should run the flow itself; the chat message
  asks GPT not to mention tool names.
- **Answers stay on the marks.** Marks carry `note` (≤200 chars) and
  `status` (`inspected` | `uncertain`). The canvas lists them under the
  photo; clicking one zooms to it. `inspected` is GPT's own claim that it
  looked at the pixels, shown as such ("GPT 表示已看過像素"), not a
  verification by Estampes.

## Pens, verification and persistent marks (0.5.4)

- **Pens.** Users pick a colour (8 swatches), a size (細/中/粗) and pen or
  highlighter (螢光筆, translucent so the photo stays visible). Marks store
  only non-default `color`, `size` and `pen`; GPT can use the same fields.
- **Verification image.** When `present_visual` draws or changes marks it
  returns a crop of them twice, original pixels and with numbered marks, so
  GPT checks alignment before saying it is done.
- **Crop coordinates.** `coordinateFrame {region, width?, height?}` lets
  GPT give coordinates read off a `process_image`/`overlay_grid` output
  (0..1 of the region, or its pixels); the server converts them.
- **Persistent marks.** Each photo keeps its marks by id for as long as the
  image is cached (about an hour). GPT edits by re-using an id, deletes with
  `remove`, starts over with `reset`, and comments on the user's marks with
  `findings` instead of redrawing them.

## Second live trial (0.5.5)

- **Undo/redo.** 上一步／下一步 (also Ctrl+Z, Ctrl+Shift+Z / Ctrl+Y) step
  through this canvas's marks, including 清除我的標註. History restarts
  after each send.
- **Users see the verification image.** A 「GPT 驗收圖」 tab appears when
  GPT drew something; it loads the same image GPT checked, on demand.
- **Photo did not load after a zoom request.** The result carried the photo,
  a processed view and the verification image (~1.2 MB) and the canvas
  received no pixels. Payloads are smaller now (display ≤1400 px JPEG q78,
  views ≤1200 px and ~220 KB), and when a result arrives without pixels, or
  none arrives within 6 s, the widget calls the app-only
  `load_visual_canvas`, which re-sends the photo, every stored mark, the
  last processed views and the verification image from the server cache.

### Same release: pen choice, exports, canvas entry, context size

- **GPT picks the pen.** The tool description tells GPT to choose colour,
  size (new `fine` < thin < medium < thick) and pen vs highlighter itself.
  To judge it, each changed mark gets an ink line in image pixels, mirroring
  the widget (pen 3 units x size, highlighter 14; the canvas is 1000 units
  wide), with warnings when a rect outline covers much of its box, a closed
  loop is barely wider than its line, a point dot is large, or a line is too
  thin to see unzoomed. The verification image now draws ink at that real
  width, so a line fatter than the feature it follows is visible to GPT.
- **Export and reload.** `/export/<id>/image.jpg` (the oriented working
  image, long side <= 4096, the frame of every coordinate) and
  `/export/<id>/marks.svg` (layers 使用者 and GPT; opens in browsers and
  vector editors). The SVG carries the marks as JSON in `<metadata>`; only
  that JSON is read back. Attaching it to a chat with the image and passing
  it as `marksFile` restores the marks (user marks as
  `replayed-unverified`, GPT marks re-validated). Links use
  `PUBLIC_BASE_URL` or Render's `RENDER_EXTERNAL_URL`; the image id is a
  content hash, so the links need no key but are unguessable. Whether
  ChatGPT passes an `.svg` attachment through `openai/fileParams` is
  unverified.
- **Opening the canvas.** GPT must call `present_visual` whenever it asks
  the user to point or circle, and whenever the user asks for the canvas
  again; not on text-only turns. ChatGPT has no button that opens an app's
  widget without the model, so the user's own entry is to say so. The
  widget can pin itself (`requestDisplayMode` pip; phones show it full
  screen) or go full screen; support per client is unverified.

## Third live trial (0.5.6)

- **Squashed photo, missing marks until the user typed.** ChatGPT can
  deliver the tool *input* after the tool *result*, and again after a chat
  message from the widget. The input has no image size and holds GPT's raw
  arguments, so the widget fell back to 1000x750 and replaced GPT's marks;
  the next resize re-applied the result. Tool input is now ignored once a
  result has been applied, and a reload requested before the host
  handshake runs right after it.
- **Polyline outline** is 1.7x the line instead of a fixed 3 units, so fine
  lines are no longer buried in their dark outline.
- `load_visual_canvas` logs as `appOnly(widget-called)` so its bytes are
  not mistaken for model context.
- Pinch/scroll zoom inside the canvas does not exist yet; in full screen a
  trackpad pinch zooms the whole page.

## Zoom inside the canvas (0.5.7)

- Pinch with two fingers (touch, or a Mac trackpad, which arrives as
  Ctrl+wheel in Chromium and as gesture events in Safari), Ctrl/⌘+wheel,
  or the －/＋ buttons zoom about the pointer, up to 24x; 整張 resets.
  Once zoomed, two-finger scroll pans, as does dragging in 移動 mode,
  with the space bar held, or with the middle button. A second finger
  cancels the stroke the first one started, so a pinch never draws.
- Drawing works at any zoom: coordinates come from the zoomed view, and
  the freehand spacing, simplification, loop and minimum-drag thresholds
  are in screen units, so fine strokes keep their detail. Ink scales with
  the zoom (it is part of the picture, the same width GPT and exports
  see); labels and endpoint dots keep their screen size.
- Above 1.5x the widget asks the app-only `load_visual_region` for the
  visible area (plus a margin) at native resolution, long side <= 2048, so
  detail is no longer limited to the 1400 px display copy. Resolution is
  still capped by the working image (long side 4096).
- In ChatGPT full screen the canvas grows to the window height.

Live trial (0.5.8): trackpad pinch, drawing while zoomed and 移動 worked.
On phones a drag sometimes scrolled the chat too, so the canvas now calls
`preventDefault` on touch events itself (iOS web views ignore
`touch-action` inside iframes). The zoom readout says 原始解析度 once the
native tile is shown; on a photo only ~1500 px wide the gain over the
1400 px display copy is small. ChatGPT's desktop "full screen" is the side
panel; the pin (PiP) button was removed as not useful.

## Layers (0.5.9)

Marks are grouped in layers so a long session can be read back step by
step and parts of it switched off.

- Every user send makes one layer (「你 · 第n次」) for the marks that are new
  in it; marks re-sent as context keep their layer.
- Every `present_visual` call that adds marks makes one GPT layer
  (「GPT · 第n次」), or GPT names it with `layer` (e.g. 「電源走線」).
  Re-using a name adds to that layer; edited marks stay in their layer
  unless `layer` is given, which moves them. Empty layers disappear;
  `reset` clears them.
- The model sees each mark's layer id and a one-line layer list
  (`L3 "電源走線" (assistant, 4)`); no geometry is repeated.
- The canvas lists layers under the photo with a checkbox each. Hiding
  is a view choice: the marks stay on the server and in GPT's context.
  Unsent marks have no layer and are always shown. Hidden layers are
  remembered per photo through ChatGPT's widget state where available.
- `marks.svg` has one Inkscape layer per Estampes layer, named the same, and
  carries the layer list in its metadata (format version 2). Attaching it
  again restores the layers under fresh ids, so they never merge with
  layers already on the canvas. Version-1 files still load (one layer per
  author).

Fix in the same release: after the user sent three arrows, every
`present_visual` call failed with "User-authored mark must be passed via
priorUserAnnotations". Root cause: GPT labelled its own trace
"YOU 3 → C105 上端", and the provenance check rejected any label starting
with "YOU ". Only ids starting `user-` and the bare form "YOU 3" are
reserved now. Also: a call that fails part-way no longer leaves its
earlier parts applied (`remove`, replayed marks, an imported marks file
were kept before), and errors name the field, the index and the mark id,
e.g. `present_visual annotations[0] (mark "x"): field label "YOU 9" …`.

Long-term tracking across days still depends on that exported file: the
server keeps a photo's canvas for about an hour in memory.

## Lifecycle and cost

Four different things, with different costs:

| Event | Model context | Notes |
| --- | --- | --- |
| Widget re-render / iframe reload (resize, scroll back) | none | ChatGPT re-fires `set_globals`; the widget ignores identical data. |
| Widget re-downloads photo / marks (`load_visual_canvas`) | none expected | App-only tool called by the widget; whether ChatGPT adds such results to the model context is unverified. |
| Model calls a tool | text + `structuredContent` | `_meta` (pixels, full mark geometry) is widget-only. |
| Images sent to the model | image tokens | Only `process_image`/`overlay_grid` outputs, `inspect_visual`, and the verification image when marks were drawn or changed (`verify:false` skips it). |

Measured before this change, the model text of `present_visual` repeated
every mark with all polyline vertices twice (text and
`structuredContent`): 3 rounds of 3 traces x 100 points grew it from 26 KB
to 103 KB per call, and a findings-only call still cost 103 KB. Now the
model gets one compact list (id, type, author, label, rounded box, vertex
count, note): 2.1 KB -> 4.3 KB for the same session, 3.6 KB for findings.
Every call logs `[size] <tool> modelText=… modelImages=… widgetOnly=…` so
Render logs show real numbers; how often ChatGPT re-runs tools per turn has
not been measured yet.

## Not yet

- Perspective correction / deskew for pages and boards (needs four corners).
- Numbered candidate regions (set-of-marks) and colour isolation.
- Grid labels cover a small corner of each cell; use a finer region if detail
  hides under a label.

## Live acceptance (ChatGPT)

1. `/version` shows `m0.5.1` (or later) and `imageTools`.
2. Refresh the connector; new chat; attach a photo and ask GPT to use
   `load_image`. The call must receive the file without any extra UI.
3. Ask for `process_image` with `clahe, sharpen` on a region; check the zoomed
   image matches the region.
4. Ask GPT to locate a feature with `overlay_grid`, then mark it with the
   returned cell centre; check the mark lands on the feature.
5. Try `imageUrl` with an image GPT found, and a GPT-generated image.
6. (M0.5.1) Ask GPT to show the photo with `present_visual` and mark a part.
   The canvas must show the real photo with a gold mark, open on the
   original, and list any processed views as extra tabs. Draw a blue mark,
   send it, and check GPT calls `process_image` on that spot.
